# DESIGN.md

## 1. Назначение приложения

TallyFinanceApp - iOS-приложение для личного учета финансов на iPhone.

Главная задача: дать пользователю максимально быстрый ручной ввод доходов, расходов и переводов между несколькими счетами. Приложение не пытается заменить банковское приложение, аналитику или бухгалтерию. Оно отвечает на простые вопросы:

- Сколько денег сейчас на каждом счете?
- Сколько осталось в конкретной категории внутри счета?
- Какие последние операции были внесены?
- Как быстро добавить новую операцию с телефона?

Приоритет продукта:

1. Скорость ввода.
2. Надежное локальное хранение.
3. Понятная структура счетов, категорий и транзакций.
4. Нативный iOS-интерфейс.
5. Минимум лишней функциональности в MVP.

## 2. Платформа и технологические ограничения

Платформа:

- iOS, только iPhone.
- Минимальная версия: iOS 17+.
- Язык: Swift.
- UI: SwiftUI.
- Локальное хранение: SwiftData для основных данных, UserDefaults для небольших настроек.
- Сервер, интернет, авторизация, облачная синхронизация: не используются.

Текущий репозиторий:

- Создан базовый SwiftUI app shell.
- Корневой экран: `RootView` с `TabView` для Dashboard, History и Settings.
- Реализованы Dashboard, Account Detail, Quick Add, History и Settings; Shortcut остается следующим функциональным этапом.
- Deployment target проекта установлен на iOS `17.0`.
- Добавлен XCTest unit test target `TallyFinanceAppTests`.
- Shared scheme `TallyFinanceApp` включает code coverage для test runs.

Базовые системные фреймворки:

- SwiftUI - интерфейс.
- SwiftData - локальная база данных.
- Foundation - даты, форматирование, decimal-логика.
- AppIntents - интеграция с Shortcuts/Siri.
- UIKit через SwiftUI-обертки только при необходимости, например для haptic feedback.

Сторонние зависимости:

- Для MVP не нужны.
- Любая новая зависимость должна быть отдельно обоснована.

## 3. Область MVP

MVP включает:

- Создание, просмотр, редактирование и удаление счетов.
- Создание, просмотр, переименование и удаление/архивация категорий внутри счета.
- Быстрое добавление расхода, дохода и перевода.
- Локальную историю транзакций.
- Ручные курсы валют.
- Общий баланс с конвертацией в основную валюту.
- Запоминание последнего счета и категории.
- Haptic feedback при сохранении транзакции.
- Shortcut/Siri Shortcut для открытия Quick Add.
- Поддержку светлой и темной темы.

Не входит в MVP:

- Графики и аналитика.
- Автоматическая интеграция с банками.
- Push-уведомления.
- Face ID, passcode lock, авторизация.
- Экспорт данных.
- iCloud sync.
- Виджеты.
- iPad/macOS layout.
- Автоматическое получение курсов валют.

## 4. Основные сущности

### 4.1 Currency

Поддерживаемые валюты:

- `CZK`
- `EUR`
- `USD`

Требования:

- Валюта счета выбирается при создании счета.
- Валюта транзакции выбирается при вводе.
- Основная валюта задается в настройках.
- Общий баланс Dashboard показывается в основной валюте.
- Курсы вводятся вручную.

Рекомендуемая реализация:

```swift
enum CurrencyCode: String, Codable, CaseIterable, Identifiable {
    case czk = "CZK"
    case eur = "EUR"
    case usd = "USD"
}
```

### 4.2 Money

Деньги нельзя хранить как `Double` в качестве источника правды.

Рекомендуемое правило:

- Хранить суммы в minor units: `Int64`.
- Например, `123.45 EUR` хранится как `12345`.
- Для CZK тоже использовать 2 десятичных знака ради единообразия, даже если пользователь чаще вводит целые кроны.
- Валюта хранится рядом с суммой.

Преимущества:

- Нет ошибок округления `Double`.
- Проще тестировать расчеты.
- Можно стабильно форматировать суммы.

### 4.3 Account

Счет - это источник денег: банковский счет, наличные, карта или другой баланс.

Поля:

- `id`
- `name`
- `currencyRawValue` persisted as `String`, exposed as computed `CurrencyCode`.
- `initialBalanceMinor`
- `createdAt`
- `updatedAt`
- `isArchived`
- Связь с категориями.
- Связь с транзакциями как source account.
- Связь с транзакциями как destination account для переводов.

Пользовательские примеры:

- Raiffeisen
- CSOB
- Наличные

Важное правило:

- Текущий баланс лучше рассчитывать как `initialBalance + transactionsEffect`, а не хранить как ручное поле, которое легко рассинхронизировать.
- Если позже производительность станет проблемой, можно добавить кешируемый баланс с обязательными тестами на инварианты.

### 4.4 Bucket / Category

Категория находится внутри конкретного счета.

Поля:

- `id`
- `account`
- `name`
- `budgetMinor`
- `limitMinor`
- `goalMinor`
- `createdAt`
- `updatedAt`
- `sortOrder`
- `isArchived`

Пользовательские примеры:

- еда
- jizdenka / йизденка
- права
- путешествия

Расчетные значения:

- `spentMinor`: сумма расходов по категории.
- `remainingMinor`: `budgetMinor - spentMinor`.
- Для доходов категория опциональна; доходы не должны автоматически уменьшать `spentMinor`.

Правило удаления:

- В MVP безопаснее не удалять категорию физически, если у нее есть транзакции.
- Рекомендуемое поведение: архивировать категорию, скрыть из обычного списка, но оставить в истории.
- Если категория без транзакций, можно удалить физически.

### 4.5 Transaction

Транзакция - неизменяемый финансовый факт, который влияет на балансы.

Типы:

- `expense`
- `income`
- `transfer`

Поля:

- `id`
- `typeRawValue` persisted as `String`, exposed as computed `TransactionType`.
- `amountMinor`
- `currencyRawValue` persisted as `String`, exposed as computed `CurrencyCode`.
- `sourceAccount`
- `destinationAccount` для переводов.
- `bucket` опционально.
- `date`
- `comment`
- `createdAt`
- `updatedAt`

Правила:

- Расход уменьшает баланс source account.
- Доход увеличивает баланс source account.
- Перевод уменьшает source account и увеличивает destination account.
- Для перевода между разными валютами MVP использует ручные курсы из настроек.
- Категория для расхода желательна, но не обязательна.
- Комментарий всегда опционален.
- Дата по умолчанию равна текущему времени.

Правило редактирования:

- В MVP можно начать без редактирования существующих транзакций, чтобы снизить риск ошибок.
- Удаление транзакции обязательно должно корректно отменять ее эффект на расчетные балансы.

Техническое решение для SwiftData:

- Enum-значения хранятся как raw string fields и открываются через computed properties.
- `sourceAccount`, `destinationAccount` и `bucket` являются optional на уровне модели, чтобы сохранить безопасное поведение при архивировании/удалении и не усложнять раннюю схему. Валидация обязательных полей будет добавлена в service/UI слоях.
- Денежные значения хранятся в `Int64` minor units.
- Exchange rates хранят decimal rate as string (`rateDecimalString`), чтобы не использовать `Double` как источник правды для пользовательского курса.

## 5. Курсы валют

Поддерживаются только ручные курсы.

Основная валюта:

- Настраивается пользователем.
- По умолчанию для пользователя в Чехии логично выбрать `CZK`.

Минимальная модель:

- `baseCurrency`
- `EUR -> CZK`
- `USD -> CZK`
- Дополнительно можно хранить обратные курсы или рассчитывать их.

Лучшее MVP-решение:

- Хранить таблицу направленных курсов для всех пар, которые нужны конвертеру.
- Пользовательский интерфейс может показывать простые поля:
  - `1 EUR = X CZK`
  - `1 USD = Y CZK`
- Если base currency не CZK, конвертер строит путь через CZK.
- Текущая реализация хранит курс как decimal string в `ExchangeRate.rateDecimalString`.
- `CurrencyConverter` сначала ищет прямой курс, затем обратный курс, затем строит путь через CZK.

Пример:

- EUR to USD = EUR to CZK / USD to CZK.
- USD to EUR = USD to CZK / EUR to CZK.

Ограничения:

- Приложение не обновляет курсы автоматически.
- Если курс не задан, общий баланс должен показывать понятное состояние: например, "нужен курс" или исключить счет из суммы с предупреждением.
- Финансовые расчеты должны быть покрыты unit-тестами.
- Отсутствующий, нулевой, отрицательный или невалидный курс является recoverable error, а не crash.

## 6. Навигация и информационная архитектура

Основная структура:

- Tab 1: Dashboard.
- Tab 2: History.
- Tab 3: Settings.

Quick Add:

- Открывается как sheet/full-screen cover с Dashboard.
- Может открываться напрямую при запуске через Shortcut.
- Должен закрываться после успешного сохранения.

Account Detail:

- Открывается из Dashboard по нажатию на счет.
- Показывает категории и последние транзакции конкретного счета.

Рекомендуемая структура SwiftUI:

- `NavigationStack` внутри каждого tab.
- `TabView` как корневая навигация.
- `sheet` или `fullScreenCover` для Quick Add. Для скорости и фокуса предпочтителен `sheet` с крупным контентом или full-screen на маленьких экранах.

## 7. Экран Dashboard

Цель:

- Быстро показать состояние счетов.
- Дать самый заметный вход в добавление транзакции.

Содержимое:

- Заголовок приложения.
- Общая сумма по всем счетам в основной валюте.
- Список счетов.
- Большая кнопка `+ Транзакция` внизу экрана.

Карточка счета:

- Название.
- Баланс.
- Валюта.
- Небольшой индикатор количества активных категорий или последних операций, если не перегружает UI.

Поведение:

- Tap по счету открывает Account Detail.
- Кнопка `+ Транзакция` открывает Quick Add.
- Если счетов нет, показывается пустое состояние с действием "Добавить счет".
- Текущая реализация открывает полноценный `QuickAddView` как sheet.
- Base currency читается из `@AppStorage("baseCurrencyRawValue")`; до Settings используется fallback `CZK`.
- Если общий баланс нельзя сконвертировать, Dashboard показывает понятное состояние вместо частичной суммы.

UX:

- Кнопка добавления должна быть доступна большим пальцем.
- Не прятать основной action в toolbar.
- Использовать SF Symbol `plus.circle.fill` или похожий.
- Избегать графиков и декоративной аналитики.
- Empty state должен оставаться компактным, чтобы на iPhone SE не пересекаться с нижней Quick Add кнопкой.

## 8. Account Detail

Цель:

- Управлять категориями конкретного счета.
- Быстро видеть последние операции по этому счету.

Содержимое:

- Название счета и текущий баланс.
- Секция категорий.
- Секция последних транзакций.
- Текущая реализация показывает последние 5 операций, где счет является source или destination.

Категория в списке:

- Название.
- Бюджет.
- Потрачено.
- Остаток.
- Прогресс-бар или компактный визуальный индикатор допустим, если он не превращается в аналитику.

Действия:

- Добавить категорию.
- Переименовать категорию.
- Изменить бюджет/лимит/цель.
- Удалить или архивировать категорию.
- Перейти к транзакциям счета.

Правила:

- Если категория используется в истории, не терять ее название.
- Не ломать историю при переименовании. В MVP можно хранить связь с категорией и отображать текущее имя; если понадобится историческое имя, добавить snapshot позже.
- Текущая реализация удаляет категорию физически только если нет связанных транзакций.
- Если категория уже используется в транзакциях, она архивируется через `Bucket.isArchived` и скрывается из активного списка.
- Архивные категории отображаются в отдельной секции Account Detail и могут быть восстановлены.
- Бюджет категории может быть `0`, если пользователь хочет использовать категорию только как тег для истории.

## 9. Quick Add

Цель:

- Внести транзакцию примерно за 5 секунд.
- Минимизировать количество тапов.

Общий поток:

1. Выбор типа: расход, доход, перевод.
2. Ввод суммы.
3. Выбор валюты.
4. Выбор счета-источника.
5. Для перевода: выбор счета-получателя.
6. Выбор категории, если применимо.
7. Комментарий, если нужен.
8. Сохранить.

Компоненты:

- Сегмент или 3 крупные кнопки типа транзакции.
- Крупное поле суммы с цифровой клавиатурой.
- Переключатель валюты `CZK / EUR / USD`.
- Горизонтальный scroll счетов.
- Чипы категорий.
- Однострочный комментарий.
- Кнопка `Сохранить`.
- Текущая реализация открывается как Dashboard sheet через `QuickAddView`.

Дефолты:

- Последний использованный счет.
- Последняя использованная категория для выбранного счета.
- Последняя валюта или валюта выбранного счета.
- Дата: сейчас.
- Тип: расход, если пользователь чаще вводит расходы. Это можно поменять позже.
- Текущие UserDefaults keys: `quickAddLastAccountID`, `quickAddLastBucketID`, `quickAddLastCurrencyRawValue`.

Валидация:

- Сумма должна быть больше нуля.
- Для расхода/дохода нужен source account.
- Для перевода нужен source account и destination account.
- Source и destination не могут быть одним счетом.
- Если валюта транзакции отличается от валюты счета, должен быть доступен курс.
- Для переводов категория не сохраняется, чтобы transfer не влиял на bucket spending.
- `QuickAddValidationService` проверяет draft до вставки `Transaction` в SwiftData.

Сохранение:

- После успешного сохранения:
  - Записать транзакцию в SwiftData.
  - Обновить remembered defaults.
  - Дать haptic feedback.
  - Закрыть Quick Add.
- При ошибке показать короткое понятное сообщение рядом с action, не системный crash.

## 10. History

Цель:

- Дать простой журнал всех операций.

Содержимое:

- Список транзакций, сгруппированный по датам.
- Фильтр по счету.
- Краткая строка операции:
  - тип,
  - сумма,
  - счет,
  - категория,
  - комментарий, если есть,
  - время.

Группировка:

- Сегодня.
- Вчера.
- Конкретная дата для более старых транзакций.

Действия:

- Swipe to delete.
- Подтверждение удаления желательно, потому что удаление влияет на баланс.
- Текущая реализация всегда показывает confirmation dialog перед физическим удалением.
- После удаления балансы счетов и категорий пересчитываются из оставшегося transaction ledger.
- Account filter учитывает счет как source и как destination для входящих переводов.
- `TransactionHistoryService` группирует записи по local calendar day и сортирует секции/операции от новых к старым.

Не входит в MVP:

- Сложные фильтры.
- Поиск.
- Экспорт.
- Массовые операции.

## 11. Settings

Цель:

- Управлять базовыми справочниками и настройками.

Секции:

- Accounts.
- Base currency.
- Exchange rates.
- App info.

Accounts:

- Добавить счет.
- Переименовать счет.
- Задать начальный баланс.
- Удалить/архивировать счет.
- Выбрать валюту счета при создании.
- Текущая реализация физически удаляет счет без истории и архивирует счет, если есть связанные транзакции.

Base currency:

- `CZK`, `EUR`, `USD`.
- По умолчанию `CZK`.
- Хранится в UserDefaults через `baseCurrencyRawValue`, который также читает Dashboard.

Exchange rates:

- `1 EUR = X CZK`.
- `1 USD = Y CZK`.
- Обновляются вручную.
- Пустое поле удаляет сохраненный курс.
- Ввод с запятой нормализуется в decimal string с точкой.

App info:

- Локальное хранение.
- Версия приложения.

Удаление счета:

- Если по счету нет транзакций, можно удалить.
- Если транзакции есть, безопаснее архивировать.
- История должна оставаться консистентной.
- Архивные счета скрываются из активного Dashboard, но доступны в Settings и могут быть восстановлены.

## 12. Shortcuts / Siri Shortcut

Цель:

- Позволить пользователю повесить действие "Добавить транзакцию" на iOS Shortcuts или Action Button на iPhone 15+.

MVP-поведение:

- В Shortcuts доступно действие `Add Transaction` / `Добавить транзакцию`.
- При запуске shortcut приложение открывается сразу на Quick Add.
- Dashboard не должен быть обязательным промежуточным экраном.

Технический подход:

- Использовать App Intents.
- Intent может быть простым: открыть приложение и выставить состояние `shouldOpenQuickAdd`.
- После старта app-level router показывает Quick Add.

Важное ограничение:

- На первом этапе shortcut не обязан принимать сумму и параметры транзакции из Shortcuts.
- Расширенный вариант можно добавить позже: параметры типа, суммы, счета и категории.

## 13. Локальное хранение

Основное хранилище:

- SwiftData.

Что хранить в SwiftData:

- Accounts.
- Buckets.
- Transactions.
- Exchange rates, если требуется структурная история/валидация.

Что хранить в UserDefaults:

- Last selected account id.
- Last selected bucket id.
- Base currency, если хранение как simple preference удобнее.
- Флаг первого запуска.
- Служебный флаг открытия Quick Add после Shortcut, если нужен.

Миграции:

- Для MVP можно начать с простой схемы.
- При изменениях модели фиксировать migration notes в `CLAUDE.md`.
- Не менять модели хаотично без учета существующих локальных данных.

Seed data:

- Не создавать реальные финансовые данные автоматически.
- Можно показать пустое состояние.
- Для разработки можно использовать preview/mock данные отдельно от production storage.

## 14. Расчет балансов

Account balance:

```text
balance = initialBalance + incomeEffects - expenseEffects + incomingTransfers - outgoingTransfers
```

Bucket spent:

```text
spent = sum(expense transactions linked to bucket)
remaining = budget - spent
```

Converted total balance:

```text
totalInBase = sum(convert(accountBalance, from: account.currency, to: baseCurrency))
```

Требования:

- Расчеты должны быть централизованы.
- Одни и те же правила должны использовать Dashboard, Account Detail и History.
- Удаление транзакции не должно оставлять "застрявшие" значения в балансе.

Текущие сервисы:

- `CurrencyConverter` - конвертирует minor-unit суммы между `CZK`, `EUR` и `USD` по ручным курсам.
- `FinancialCalculationService` - рассчитывает текущий баланс счета из `initialBalanceMinor` и transaction effects.
- `BucketCalculationService` - рассчитывает `spentMinor` и `remainingMinor` для категории.
- `QuickAddValidationService` - проверяет Quick Add draft и создает `Transaction`.
- `TransactionHistoryService` - фильтрует, группирует и удаляет операции History.

Фактические правила Stage 4:

- Expense создает отрицательный delta для source account.
- Income создает положительный delta для source account.
- Transfer создает отрицательный delta для source account и положительный delta для destination account.
- Deletion/reversal считается исключением удаляемой транзакции из ledger, а не отдельной мутацией баланса.
- Bucket spending учитывает только expense-транзакции, связанные с bucket; income и transfer не уменьшают bucket remaining.
- Все результаты возвращаются в minor units валюты целевого счета или owning account bucket.

Coverage после Stage 4:

- App target: `91.14%`.
- `CurrencyConverter`: `98.98%`.
- `FinancialCalculationService`: `95.89%`.
- `BucketCalculationService`: `95.45%`.

## 15. Форматирование и ввод денег

Ввод:

- Цифровая клавиатура.
- Разрешить десятичный разделитель.
- Нормализовать `,` и `.`.
- Запрещать отрицательные суммы в поле ввода.

Отображение:

- Использовать locale-aware formatting.
- Показывать код валюты рядом с суммой.
- Не скрывать валюту, потому что приложение мультивалютное.

- `1 250 CZK`

- `10.00 USD`

## 18. Ошибки и пустые состояния

Пустой Dashboard:

- Сообщить, что счетов еще нет.
- Дать кнопку "Добавить счет".

Нет категорий:

- Сказать, что категории можно добавить для выбранного счета.
- Quick Add должен позволять сохранить без категории.

Нет курсов:

- Для общего баланса показать, что часть счетов не сконвертирована.
- В Settings подсветить отсутствующий курс.

Ошибка сохранения:

- Не терять введенные данные.
- Показать короткое сообщение.

## 21. Ограничения и риски

Риски:

- SwiftData-модели нужно проектировать аккуратно, потому что миграции локальных данных могут быть болезненными.
- Балансы легко рассинхронизировать, если хранить их как mutable field. Поэтому MVP должен рассчитывать баланс из транзакций.
- Переводы между валютами требуют четкого правила конвертации.
- Quick Add может стать перегруженным, если попытаться добавить все поля сразу.
- Shortcut-интеграцию нужно тестировать на реальном устройстве или в среде, где доступны Shortcuts/App Intents.

Решения для снижения риска:

- Сначала реализовать стабильные модели и расчеты.
- Покрыть расчеты unit-тестами.
- Сделать Quick Add простым и расширять только после ручной проверки.
- Хранить out-of-scope идеи отдельно, не смешивать с MVP.

## 22. Открытые вопросы перед реализацией

Эти вопросы не блокируют создание плана, но должны быть решены до или во время ранних этапов разработки:

- Нужно ли разрешать начальный баланс счета при создании, или сначала создавать счет с нулем?
- Нужно ли редактирование транзакций в MVP, или достаточно удаления и повторного ввода?
- Нужно ли архивирование счетов в UI MVP, или пока блокировать удаление счета с историей?
- Какой язык интерфейса использовать в первом MVP: русский, английский или смешанный?
- Должны ли категории иметь бюджет обязательно, или можно создавать категорию без бюджета?
- Для переводов между разными валютами достаточно ли автоматического расчета по ручному курсу, или пользователь должен видеть рассчитанную сумму до сохранения?

Рекомендуемые ответы для MVP:

- Начальный баланс нужен при создании счета.
- Редактирование транзакций отложить.
- Счета и категории с историей архивировать, а не удалять.
- Первый интерфейс сделать на русском, потому что запрос и доменная модель описаны на русском.
- Бюджет категории сделать опциональным или разрешить `0`.
- Для валютного перевода показывать рассчитанную сумму перед сохранением.

## 23. Acceptance Criteria для MVP

MVP считается готовым, если:

- Пользователь может создать минимум два счета в разных валютах.
- Пользователь может создать категории внутри счета.
- Пользователь может добавить расход меньше чем за несколько тапов после первого ввода.
- Доход корректно увеличивает баланс счета.
- Расход корректно уменьшает баланс счета и влияет на категорию.
- Перевод корректно меняет балансы двух счетов.
- Dashboard показывает список счетов и общий баланс в основной валюте.
- История показывает операции по датам.
- Swipe delete удаляет транзакцию и расчетные балансы меняются корректно.
- Settings позволяют задать основную валюту и ручные курсы.
- Последние счет и категория подставляются при следующем Quick Add.
- При сохранении срабатывает haptic feedback.
- Shortcut открывает приложение сразу в Quick Add.
- Все данные остаются локальными.
